# 测试用例1：后端开发工程师（社招3-5年）

## 一句话画像

寻找**具备系统性工程思维、能独立承担模块开发、同时具备良好协作素养的中级工程师**——不仅能交付功能，更能理解技术债务、考虑长期可维护性。

---

## 一级胜任力维度（MECE）

| 维度 | 名称 | 核心定义 |
|------|------|----------|
| D1 | 方向与标尺 | 对代码质量和架构合理性的内在判断标准 |
| D2 | 内驱与主动 | 在无人督促时主动发现并解决问题的倾向 |
| D3 | 韧性与稳定性 | 在复杂问题、模糊需求下保持持续推进的能力 |
| D4 | 认知与进化 | 对系统全局的理解深度以及技术学习能力 |
| D5 | 专业成熟度 | 工程实践的规范意识与落地能力 |
| D6 | 协作与影响 | 在团队中有效沟通、推动共识的能力 |

---

## 各维度详细定义

### D1 方向与标尺
**定义**：工程师对"什么是好代码"、"什么是合理架构"的内在判断标准，决定了其在无人监督时的产出质量。

**为什么重要**：中级工程师需要开始独立做技术决策，方向感决定了其是否能持续产出高质量、可维护的代码。

### D2 内驱与主动
**定义**：不需要外部驱动就能识别问题、提出改进、主动承担责任的倾向。

**为什么重要**：3-5年经验者应从"完成任务"进化到"发现问题并推动解决"，这是从执行者到骨干的分水岭。

### D3 韧性与稳定性
**定义**：面对复杂 bug、线上故障、模糊需求时，能保持冷静、持续排查直到解决问题的能力。

**为什么重要**：中级工程师开始承担核心模块，线上问题的处理质量直接影响业务稳定性。

### D4 认知与进化
**定义**：对系统全貌的理解深度，以及在新技术/新领域面前的快速学习能力。

**为什么重要**：技术迭代快，能持续进化的工程师才能保持竞争力，避免3年经验用5年。

### D5 专业成熟度
**定义**：对工程规范（code review、测试、文档、部署）的理解和主动践行。

**为什么重要**：3-5年应形成规范意识，不再需要外部强制推动才能写测试、写文档。

### D6 协作与影响
**定义**：在跨团队协作、技术方案评审、知识分享中有效沟通、推动共识的能力。

**为什么重要**：中级工程师开始参与核心讨论，需要影响他人、贡献技术判断。

---

## 可观察行为（每个维度2-3条）

### D1 方向与标尺
- 提交代码时主动考虑边界情况、异常处理
- 在 code review 中不仅指出问题，还能给出更好的实现建议
- 对历史代码的"坏味道"有警觉，会主动记录改进想法

### D2 内驱与主动
- 发现系统隐患时不会等别人来修，会主动认领或上报
- 主动关注业务指标，当指标异常时会主动排查
- 主动承担团队基础设施类工作（CI/CD、监控、文档）

### D3 韧性与稳定性
- 复杂 bug 面前能拆解问题、分步排查，不轻易放弃
- 线上故障时能保持冷静，按优先级处理而非慌乱
- 面对需求变更或方向调整时能快速调整节奏

### D4 认知与进化
- 能清晰描述所负责模块在整个系统中的位置和上下游依赖
- 主动学习团队技术栈之外的相关知识
- 能将学习到的新技术/新理念用业务语言解释给非技术人员

### D5 专业成熟度
- 写新功能时主动补充单元测试
- 代码变更主动更新相关文档
- 参与 code review 时能提出建设性意见，不只是挑错

### D6 协作与影响
- 技术方案设计时主动拉相关方讨论、收集反馈
- 能清晰表达技术决策的 trade-off，不只说结论
- 主动参与技术分享，帮助团队沉淀知识

## 角色证据（验证点）

| 行为 | 典型证据 |
|------|----------|
| 代码质量意识 | 历史上提出的 code review 意见质量、被合并的设计文档 |
| 主动发现问题 | 主动修复的技术债务、提出的优化提案、预防的线上事故 |
| 复杂问题处理 | 解决的复杂 bug 案例、故障复盘报告、排查思路 |
| 系统理解 | 能画出的系统架构图、对上下游依赖的理解程度 |
| 工程规范 | 测试覆盖率、代码规范遵循情况、文档完善度 |
| 跨团队协作 | 参与的跨团队项目、推动的技术改进、与产品/运营的协作质量 |

---

## 验证结论

**基于字节跳动、阿里云、腾讯官网校招/社招信息的交叉验证：**

1. ✅ **方向与标尺** — 各公司均强调"代码质量"、"可维护性"，确认为核心特质
2. ✅ **内驱与主动** — 腾讯明确提到"主动发现问题"，阿里强调"主人翁意识"
3. ⚠️ **协作与影响** — 各公司均有提及，但表述方式不同，需根据实际团队规模调整期望
4. **工具栈**（如 K8s、Redis、微服务框架）应作为 D4 认知的**证据层**，而非独立维度

---

## 适用边界

**适合用于：**
- 中级后端工程师的招聘筛选
- 1-3年工程师的晋升评估
- 团队内部的技术人才盘点

**不适合用于：**
- 校招生（标准偏高，应使用校招专用模型）
- 资深专家/架构师（需补充架构决策、技术规划维度）
- 纯管理岗（需增加团队管理、战略对齐维度）
