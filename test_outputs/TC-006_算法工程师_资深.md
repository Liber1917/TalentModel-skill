# 测试用例6：算法工程师（推荐方向，资深P7+）

## 一句话画像

寻找**兼具深厚算法功底与系统工程能力、能洞察业务目标、主导技术方向并带动团队突破的算法专家**——他不仅能解决眼前的 CTR 问题，更能定义下一代推荐系统的技术路线。

---

## 一级胜任力维度（MECE）

| 维度 | 名称 | 核心定义 |
|------|------|----------|
| D1 | 技术深度 | 在推荐/排序领域的算法积累与对业界前沿的持续跟踪 |
| D2 | 系统思维 | 将算法方案落地为大规模可靠系统的工程判断力 |
| D3 | 业务洞察 | 理解推荐业务目标，将技术价值转化为可度量业务价值 |
| D4 | 技术领导力 | 主导方向、定义标准、培育团队、跨团队技术影响 |
| D5 | 数据驱动 | 构建指标体系、设计可靠实验、用数据为技术决策背书 |
| D6 | 创新突破 | 在核心问题上识别突破口、推动落地并沉淀方法论 |

---

## 各维度详细定义

### D1 技术深度
**定义**：对召回、粗排、精排、重排全链路的算法理解，以及对 Transformer、多任务学习、因果推断等业界主流方向的掌握和判断。

**为什么重要（P7+视角）**：资深专家需要能对业界顶会论文做出独立判断（"这个方法在我们的场景有没有价值"），而非只跟风复现。

### D2 系统思维
**定义**：理解算法在大规模工程系统中的约束（延迟、吞吐、存储、成本），并能在算法效果与工程成本之间做出成熟 trade-off。

**为什么重要**：P7+需要对系统全局负责，"好算法跑不起来"是资深工程师的典型问题。

### D3 业务洞察
**定义**：能将推荐系统的技术指标（点击率、转化率）与业务目标（GMV、留存、内容生态健康）建立清晰的映射关系，避免"指标好但业务没变化"的陷阱。

**为什么重要**：P7+需要能和业务方对话，而不只是向下对技术负责。

### D4 技术领导力
**定义**：制定技术 OKR、定义代码/实验规范、主持 design review、培养低级别同学的综合能力。

**为什么重要**：P7+的杠杆来自于带动团队，个人产出只是基础，更重要的是"通过别人完成更大的事"。

### D5 数据驱动
**定义**：能设计严谨的 A/B 实验（避免 HARKing、辛普森悖论）、识别指标体系的漏洞、从实验结论中提炼可复用的决策规则。

**为什么重要**：推荐系统是靠实验驱动的，P7+需要保证团队的实验文化是严谨的，而非"怎么做都能跑出好结果"。

### D6 创新突破
**定义**：在团队遇到瓶颈时，能识别突破口（可能来自论文、相邻领域、工程优化），推动落地并沉淀为可复用的方法论。

**为什么重要**：P7+需要推动技术进步，而不只是维护现状。

## 可观察行为（每个维度2-3条）

### D1 技术深度
- 能清晰讲解近2年 RecSys/SIGIR/KDD 中与自己业务相关的核心论文，并说明是否值得复现
- 面对新算法方案，能给出"在我们场景的收益预估"和"关键假设是什么"
- 对召回到重排全链路有独立的技术判断，不只是负责某个环节

### D2 系统思维
- 在设计算法方案时，主动考虑 P99 延迟约束、服务容量、模型更新频率
- 能描述一次"为了工程可行性主动降级算法复杂度"的决策，并说明 trade-off
- 能清晰画出推荐系统的数据流向和各模块的依赖关系

### D3 业务洞察
- 能说出一个"技术指标提升但业务指标没动"的案例，及其原因分析
- 主动参与业务讨论，不等业务提需求，而是主动识别业务问题
- 能用业务语言（而非算法语言）向 GM/VP 汇报技术方案的价值

### D4 技术领导力
- 团队中有被其 mentor 的同学显著成长的案例
- 主导过至少一次整体技术方向的评审（技术路线选择、重大重构）
- 跨团队有良好口碑：基础架构/平台团队愿意为其优先排期

### D5 数据驱动
- 能识别团队内 A/B 实验的系统性问题（如 novelty effect、数据泄漏、指标冲突）
- 建立或优化过指标体系，能说明为什么旧指标不够好
- 能从一系列实验结论中归纳出可复用的经验规律

### D6 创新突破
- 有过一个显著提升核心指标的创新项目，能说明突破点在哪
- 能分辨哪些论文方法"在学术上合理但工业落地困难"
- 在业务遇到瓶颈时，是团队中主动提出新思路的人

## 角色证据（验证点）

| 行为 | 典型证据 |
|------|----------|
| 技术深度 | 发表的论文/专利、技术博客、内部技术分享记录 |
| 系统思维 | 主导的系统设计文档、解决的线上稳定性问题案例 |
| 业务洞察 | 跨技术/业务的汇报材料、OKR 与业务目标的对齐情况 |
| 技术领导力 | 团队成员的晋升记录、design review 频率与质量 |
| 数据驱动 | 实验报告质量、指标体系设计文档 |
| 创新突破 | 核心指标提升的项目复盘、内部分享/KM 文章 |

## 验证结论

**基于字节跳动、快手、阿里妈妈算法工程师高级岗位的交叉验证：**

1. ✅ **技术深度 + 系统思维** — 三家公司均强调"算法+工程"两手抓，P7+不能只懂算法不懂系统
2. ✅ **业务洞察** — 字节跳动明确要求"理解推荐业务目标"；快手强调"业务驱动的算法设计"
3. ✅ **技术领导力** — P7+以上均强调"带团队"、"主导方向"；纯个人贡献者卡在 P6-P7
4. ⚠️ **创新突破** — 各公司表述不同（"技术前瞻性"/"pushing state of art"），但本质一致
5. **Embedding/Transformer/因果推断** 等具体技术 → 证据层，不作独立维度
6. **注意**：P7+对"学习敏捷"已不适用，替换为"创新突破"——不再是快速学习已知方法，而是在未知领域开路

## 适用边界

**适合用于：**
- 推荐/广告/搜索方向算法工程师 P7+/高级/专家级招聘
- 算法技术专家的晋升评估
- 技术猎聘候选人的能力校准

**不适合用于：**
- P4-P6 算法工程师（应降低 D4/D6 预期，以 D1/D2 为主）
- 校招算法岗（需完全调整为潜力维度）
- 机器学习平台/工程岗（D2 系统思维需拆为独立的工程能力维度）
