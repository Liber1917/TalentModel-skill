## 一句话结论

**旧流程的核心问题：** 维度草案基于预设的"互联网大厂视角"框架，所有用例骨子里都是同一套互联网工程师标准。

**新流程的核心改变：** 在建模之前先采集多类型企业的原始信息，用信号归纳表驱动维度草案，而非预设框架。

## 改动明细

### 1. 新增 Step 0：企业分布探索（前置）

在配置向导之前，先通过 WebFetch 了解"这个岗位在哪些类型企业分布"，让用户知道需要覆盖多元类型再选验证公司。

**TC-001 验证公司：** 字节跳动、阿里云、腾讯 → 全部是互联网大厂
**Step 0 输出：**
```
企业类型数：1 种（⚠️ 单一类型）
覆盖类型：互联网大厂
→ ⚠️ 未满足多元化要求，建议补充其他类型企业
```

旧报告：完全没有这个步骤，直接进入建模，默认"验证公司 = 大厂"。

### 2. 官网验证前移至 Step 3.5

旧流程：Step 8（建模后验证）→ 变成了"找证据支持已有框架"。

新流程：Step 3.5（建模前采集）→ 产出"原始信号归纳表"，让维度草案由证据驱动。

### 3. 大厂特有信号被明确降级

**TC-001 新流程 D4 "专业成熟度"建模备注：**

```
  - 高并发/分布式系统经验 → 降为D4的证据层

  - 快速迭代/敏捷开发 → 降为D4的证据层
  - 数据驱动/AB测试 → 降为D4的证据层
```

旧报告的 D4 是"认知与进化"，高并发、算法学习能力被直接作为维度要求，没有降级处理。

### 4. 行业定制维度（TC-009 金融科技工程师）

## 核心结论

**① 旧流程的8个用例（TC-001~008）都有大厂偏差风险**
→ 验证公司全为互联网大厂，没有 Step 0 来触发警告
→ "高并发/算法/快速迭代"这些大厂特有要求被当作普适维度

**② 新流程能识别并降级大厂特有要求**
→ 通过信号归纳表，明确标注每个信号来自哪种类型企业
→ 大厂特有信号进入证据层，而非一级维度

**③ 行业定制维度在多类型企业中自然浮现**
→ TC-009 金融科技：D3 = 合规意识与风险判断
→ TC-010 智能制造：D3 = 工程落地与系统思维
→ 这些维度在旧流程中也有，但新流程的推导路径更透明

**④ 残留问题：测试用例本身的多样性不足**
→ TC-001~008 的 VALIDATION_COMPANIES 配置本身就是纯大厂
→ 这是测试数据问题，不是 Skill 逻辑问题
→ 真实用户场景中，Step 0 的警告机制会引导用户补充其他类型企业
